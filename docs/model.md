# The ARPL model

## Lookup chain

An agent (or a person) facing a task looks it up in this order:

1. **Project workflow** (Level 4): is there a composed sequence for this deliverable and project type? (`project-workflows/`)
2. **Discipline workflow** (Level 3): a pattern plus the domain overlay for the discipline (`domains/`).
3. **Pattern** (Level 2): the reusable production technique (`library/`).
4. **Primitive** (Level 1): one API operation and its pitfalls.

Moving down the chain adds API detail; moving up adds professional context. The rule of the project: *teach professional practice downward until the required API action becomes obvious.*

## Facets

Every pack carries facets from [the vocabularies](../vocabularies/vocabularies.json): workflows, disciplines, roles, project types, phases, Revit versions tested, failure patterns. Facets are lists: one pack can serve many disciplines. The pack's folder is its first workflow; the catalogs list it everywhere else.

## Work classes

Work class is the facet that decides **method**: what preview to show before committing, and what counts as proof that the work is done. See [work-classes.md](work-classes.md).

## Single source of truth

Manifests are the only place facts about a pack live. Catalogs are generated by `tools/build_catalogs.py`; `tools/validate.py` checks every manifest against `schema/manifest.schema.json` and the vocabularies.
